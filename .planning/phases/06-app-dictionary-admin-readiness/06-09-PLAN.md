<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Mobile/web clients -> shared account APIs | Cookie or Bearer credentials cross into profile, refresh, logout, and emergency-contact endpoints. |
| Refresh token -> session renewal | A persisted token can outlive user deactivation unless checked server-side. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-12 | Spoofing | Shared account APIs | mitigate | Verify cookie and Bearer credentials through `getAuthenticatedUser`; reject inactive users before returning profile/contact data or refreshing tokens. |
| T-06-15 | Information Disclosure | Profile/contact responses | mitigate | Use explicit response fields and omit password hashes, refresh tokens, provider secrets, and admin-only fields. |
| T-06-16 | Elevation of Privilege | Refresh/session APIs | mitigate | Load token owner, reject `User.isActive = false`, and invalidate the presented refresh token when appropriate. |
| T-06-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs no packages. |
</threat_model>
